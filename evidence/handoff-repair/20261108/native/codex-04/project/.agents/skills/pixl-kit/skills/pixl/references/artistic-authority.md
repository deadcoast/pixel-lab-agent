# Preserve artistic requirement authority

Read when translating an aesthetic brief into prompts, rejection criteria, or a review. The cases below document observed failure modes; their measured values are not universal pixel-art rules.

For delegated work, use the [request and criteria handoff](request-review.md) so the caller can inspect the actual artifacts independently. A self-audit is useful correction work, but its conclusion is not the caller's acceptance.

Every production approach carries a compact authority table: property/value, requirement versus observation/proposal, exact source, and applicable scope. Carry the user's requested aesthetic into the derived prompts and checks. An image interpretation that differs from the brief is a reported uncertainty, not permission to replace that treatment. Only established project requirements become production rejection rules; proposals define labeled experiments. A measured color, gap, alpha level, component count or diagnostic contrast result remains an observation until adopted. Before the final handoff, reconcile every enforced restriction in the whole approach with that table; remove unsupported approval claims and keep diagnostic conclusions within their tested conditions.

When the brief specifies a treatment, the proposed sample, production instructions and review criteria must all explicitly retain it. For requested selective anti-aliasing and partial transparency, describe where those treatments will be authored and how they will be reviewed; a reference interpretation such as “glow” does not replace either requirement. Uncertainty about a new shape calls for a treatment-preserving experiment, not a default ban on that shape or treatment. When no fixed palette is imposed, production checks omit exact palette membership; a palette experiment remains optional. Describe matching quality, lighting intent and provider reliability as interpretations or untested expectations unless evidence establishes them. A plan or a copied reference recipe cannot guarantee those outcomes.

Test each derived restriction against a variation that still satisfies the brief. If that variation could fail the check, the extra restriction is a proposal, not an entailed requirement. Two detached antenna islands, for example, do not forbid another intentional detached detail or require the reference's total component count, coordinates or gap rows. Apply the same scope check to planned failure conclusions: one failed candidate establishes that attempt's failure, not a provider's general inability. A fallback can address that attempt without claiming a universal limit.

After saving an approach, reopen and read the complete file before the final response. Audit the actual provider prompt, every proposed rejection check and every fallback conclusion against the authority table; reviewing the table or selected sections alone does not complete this step. For each added restriction, either identify its adopted source or label it as an optional experiment and remove it from production rejection rules. In a proposed experimental prompt, label the extra choices as proposals at the prompt itself. Correct contradictions such as an open alpha policy followed by an unexplained “no antialiasing” directive, or a qualitative color requirement turned into an invented numeric hue threshold. Preserve the earlier draft when revising it and report the scope and any unresolved conflict from this whole-file audit.
