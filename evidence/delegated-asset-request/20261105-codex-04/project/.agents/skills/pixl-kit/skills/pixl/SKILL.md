Use the [production workflow](references/production.md) for asset work and the [runtime boundary](references/runtime.md) for state operations or MCP wiring. Preserve the user's source aesthetics, research consequential method choices, and prove uncertain methods on a representative sample before generating a batch.

Use the [source-grounded knowledge operation](references/knowledge.md) to answer a production question from the actual supplied sources. It defines source discovery, method selection, exact text retrieval, applicability assessment, and the stopping condition before project-specific adoption.

Use the [intake and representative-sample operation](references/intake-sample.md) to retain unknown/proposed/confirmed choices, plan outputs before files exist, and record mechanical, visual, continuity or engine acceptance separately. Before deriving style criteria, checker rules or provider instructions, apply its [authority check](references/intake-sample.md#keep-authority-through-derived-rules). Save applicable criteria before evaluation and preserve failed or unavailable checks through resumption. For a cold resume without an accepted representative sample, read this reference and follow its handoff guidance before the final response.

Every production approach carries a compact authority table: property/value, requirement versus observation/proposal, exact source, and applicable scope. Carry the user's requested aesthetic into the derived prompts and checks. An image interpretation that differs from the brief is a reported uncertainty, not permission to replace that treatment. Only established project requirements become production rejection rules; proposals define labeled experiments. A measured color, gap, alpha level, component count or diagnostic contrast result remains an observation until adopted. Before the final handoff, reconcile every enforced restriction in the whole approach with that table; remove unsupported approval claims and keep diagnostic conclusions within their tested conditions.

When the brief specifies a treatment, the proposed sample, production instructions and review criteria must all explicitly retain it. For requested selective anti-aliasing and partial transparency, describe where those treatments will be authored and how they will be reviewed; a reference interpretation such as “glow” does not replace either requirement. Uncertainty about a new shape calls for a treatment-preserving experiment, not a default ban on that shape or treatment. When no fixed palette is imposed, production checks omit exact palette membership; a palette experiment remains optional. Describe matching quality, lighting intent and provider reliability as interpretations or untested expectations unless evidence establishes them. A plan or a copied reference recipe cannot guarantee those outcomes.

Test each derived restriction against a variation that still satisfies the brief. If that variation could fail the check, the extra restriction is a proposal, not an entailed requirement. Two detached antenna islands, for example, do not forbid another intentional detached detail or require the reference's total component count, coordinates or gap rows. Apply the same scope check to planned failure conclusions: one failed candidate establishes that attempt's failure, not a provider's general inability. A fallback can address that attempt without claiming a universal limit.

After saving an approach, reopen and read the complete file before the final response. Audit the actual provider prompt, every proposed rejection check and every fallback conclusion against the authority table; reviewing the table or selected sections alone does not complete this step. For each added restriction, either identify its adopted source or label it as an optional experiment and remove it from production rejection rules. In a proposed experimental prompt, label the extra choices as proposals at the prompt itself. Correct contradictions such as an open alpha policy followed by an unexplained “no antialiasing” directive, or a qualitative color requirement turned into an invented numeric hue threshold. Preserve the earlier draft when revising it and report the scope and any unresolved conflict from this whole-file audit.

Start cold sessions with family, workflow and job reports.

The compiled operational knowledge is [library.px](../../resources/knowledge/library.px). Retrieve one method with `context <resolved library.px> k.<method-id> --root <resolved resources directory>`. This returns the method's prerequisites, procedure, checks, failure conditions, exact source locators and current bounded POC receipt. Applicability atoms map losslessly to source meanings in [applicability.json](../../resources/knowledge/applicability.json). Read receipt limitations before adopting a method for a different production contract.

The bundled runner is `../../scripts/pixl.py`; the runtime is `../../runtime/`. Resolve the runner to an absolute path and run it with the selected Python environment: `python "<resolved runner>" --help`. It requires Python 3.11+, Pillow 10+, and jsonschema 4.18+; install the bundled `../../requirements.txt` into the selected environment. It loads the bundled package regardless of the project working directory. Keep mutable state and outputs in the user's project. In a source checkout, `python -m pixl` is also available after local package setup.

Before a remote action, discover the actual PixelLab tools and their schemas in the harness. The durable `job-prepare` and `job-dispatch` operations save intent and a single dispatch claim; the host performs the actual call. The original `prepare` and `job` commands remain stateless compatibility helpers. No local tool submits, polls, authenticates to, or generates with PixelLab. Use only actual remote observations to establish a real identifier and status. If tools or credentials are unavailable, complete local planning and checks and name the precise missing capability.

Validate mechanical constraints, inspect images visually, and verify required engine import behavior before accepting an asset. Report what was checked and what remains uncertain. Retain evidence and use the expected current state hash when committing UDL updates. Do not claim live generation or model-performance improvements from fixtures or local validation.
