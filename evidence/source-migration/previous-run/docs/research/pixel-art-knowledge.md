# PIXL pixel-art knowledge and research decisions

This document explains the curated registry in [knowledge/pixel-art.json](../../knowledge/pixel-art.json). The registry contains **43 actionable methods**, each with applicability, prerequisites, a procedure, checks, pitfalls, exact local source ranges, and a reproducible proof-of-concept recipe. Research was checked on **2026-09-10**.

**Execution status:** every `poc` in this registry is a recipe; actual observations are recorded separately. The offline runner in [pixl/poc.py](../../pixl/poc.py) contains **39 bounded reference checks covering all 43 methods**, mapped in [method-proof-coverage.json](../../methods/method-proof-coverage.json). The complete reference run passed all 39 checks. Reports bind the runner's `implementation_sha256`, the resolved registry's `knowledge_sha256`, and every uniquely cited original file in `source_sha256`, alongside observations and output-artifact hashes. Missing knowledge or cited source bytes prevent an unbound passing report. This proves the specified primitives, not full PixelLab, engine, performance or aesthetic behavior. The recipes were designed during this curation; they are not a claim that the cited sources used these exact fixtures.

## Corrections and evidence limits

1. **Dither coverage:** the report's 4×4 masks labeled 25%, 50% and 75% at lines 717–734 contain 1, 4 and 8 selected cells respectively: **6.25%, 25% and 50%**. The curated `dither-coverage` fixture instead specifies a rank matrix and checks populations of 4, 8 and 12. The originals are preserved.
2. **Historical citation tokens:** the local reports contain tokens such as `turn20view0`, without a reusable source URL map. They identify the old research's claims but do not independently verify them here. L1 below means a local proposed method, with local source ranges; it never means a newly confirmed implementation fact.
3. **Game-specific attribution:** the report itself rejects the unverified Metal Slug skeletal claim and Arco subpixel-pipeline claim at lines 13–18 and 1584–1645. This registry makes neither claim. Owlboy and Eastward workflow statements remain historical claims in the local source unless separately reverified; they are unnecessary to make the general methods useful.
4. **Noita specificity:** the primary GDC page confirms that Petri Purho discussed scaling falling-sand simulation and integrating destructible rigid bodies. Its retrieved summary does not establish the precise chunk dimensions, write-halo shape, or full memory layout. Those details remain local case-study claims. The registry validates influence bounds and ownership instead of prescribing a magic chunk size. [GDC session](https://www.gdcvault.com/play/1025695/Exploring-the-Tech-and-Design)
5. **Palette and lighting:** multiplying a diffuse color by a quantized scalar can still create colors outside an approved palette. Exact palette output requires a ramp lookup or explicit allowed-color mapping. The source's light-band formula also needs finite input, clamping and `K >= 2` as implementation preconditions. See the source discussion at [report lines 1078–1126](../../training/original-docs/PIXEL-ART-DEEP-RESEARCH.md).
6. **Sampling and lighting:** nearest image sampling does not force a renderer's lighting or shadow buffer to use the logical sprite resolution. Godot explicitly distinguishes texture filtering from light/shadow evaluation at viewport resolution. The registry therefore requires a separate lighting-grid contract. [Godot lighting documentation](https://docs.godotengine.org/en/stable/tutorials/2d/2d_lights_and_shadows.html)
7. **Clusters and style:** source singleton checks and palette restrictions are scoped constraints. Stars, eyes, spark particles, rough clusters, partial alpha, smooth lighting and deformation can all be deliberate. Metrics flag a deviation from a stated brief; they do not establish a universal aesthetic rule.
8. **Capabilities:** a PixelLab image may be a candidate for a normal map, terrain tile or rig attachment. A prompt cannot certify correct axes, connected terrain, sockets, physical behavior, render support or live API capability. Validate the returned artifact and consult the kit's actual capability contract before issuing a tool request.

## Registry contract

`version` is 1. `methods` is an array with stable string IDs. Each entry contains `title`, `applies_to`, `requires`, `procedure`, `checks`, `pitfalls`, `sources`, and `poc`. The arrays are intentionally inspectable instructions rather than executable source code.

Every local `sources` entry is `{path,start,end}` using a repository-relative path and inclusive one-based lines. Sources document motivation, context or the precursor method; newly designed checks are identified here as curation proposals. Primary web support is mapped in the decision table below so that a source's documented capability is not confused with a local language feature.

A consumer should first match `applies_to`, satisfy `requires`, and select only checks relevant to the chosen profile. Unsupported methods should remain available as knowledge, with explicit unsupported execution status. Hard technical invariants and visual-review judgments must have separate result fields. Never synthesize a passing POC report from a recipe.

## Primary evidence and what it establishes

These sources were retrieved during this curation. Their documentation describes their own tools; no statement below is a PIXL or PixelLab implementation promise.

- **P1:** Aseprite distinguishes RGBA from palette-indexed pixels and defines a transparent index for transparent indexed layers. That supports keeping index identity, color meaning and alpha policy explicit. [Color modes](https://www.aseprite.org/docs/color-mode/)
- **P2:** Raymond Schlitter's artist-authored tutorial discusses deliberate pixel placement and same-color clusters, including both angular and organic cluster styles. This is a practitioner's teaching, not a universal quality theorem. The silhouette and contour fixtures in the registry are our proposed review mechanisms. [Back to Basics](https://www.slynyrd.com/blog/2018/5/16/pixelblog-5-back-to-basics)
- **P3:** Tiled distinguishes corner, edge and mixed terrain sets. Binary complete corner and edge sets each have 16 patterns; a complete binary mixed set has 256. It also supports weighted variants and controlled tile transformations. Those facts motivate explicit topology and transform contracts; the registry's bit order and deterministic fixture are our own. [Using terrains](https://docs.mapeditor.org/en/stable/manual/terrain/)
- **P4:** Tiled's image-based tilesets use fixed tile dimensions plus optional margin and spacing; image-collection tilesets can contain differently sized images. This supports explicit import metadata. It does not prove that a texture is visually seamless. [Editing tilesets](https://docs.mapeditor.org/en/stable/manual/editing-tilesets/)
- **P5:** Aseprite documents sprite-sheet offsets, cell dimensions, padding, ordering and export selection. Our extraction and restoration checks validate the resulting data independently of any particular exporter. [Sprite sheets](https://www.aseprite.org/docs/sprite-sheet/)
- **P6:** MDN documents Canvas `imageSmoothingEnabled` as a scaled-image smoothing control whose default is true. Our device-pixel fixture checks the actual enlargement rather than assuming a setting guarantees the displayed result. [Canvas image smoothing](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled)
- **P7:** Godot documents normal/specular textures, light occluders and viewport-dependent light/shadow evaluation as separate facilities. This supports explicit channels, visibility and resolution boundaries. Our numeric shading fixtures are illustrative algorithms rather than a claim about the exact Godot shader. [2D lights and shadows](https://docs.godotengine.org/en/stable/tutorials/2d/2d_lights_and_shadows.html)
- **P8:** Aseprite documents frame operations, durations, tagged ranges, reuse and onion-skin previews. These features support explicit timing and comparative frame review. The contact and event rules in the registry are proposed contracts. [Animation](https://www.aseprite.org/docs/animation/)
- **P9:** Spine documents slots as attachment containers, one active attachment per slot, a separate draw-order list and keyable attachment selection. It also describes blend modes that may affect draw calls. The registry borrows this conceptual separation; it does not require a Spine runtime. [Slots](https://esotericsoftware.com/spine-slots). The developer's attachment documentation describes how attachments follow bone transforms. [Attachments](https://en.esotericsoftware.com/spine-unity-attachments-and-attachmenttools)
- **P10:** The authors of *Analysis and Compilation of Normal Map Generation Techniques for Pixel Art* study generation methods in the context of pixel-art-specific constraints. This is relevant research supporting validation of generated maps, not evidence that one automatic conversion is always correct. [Research paper](https://arxiv.org/abs/2212.09692)
- **P11:** The GDC session summary identifies Petri Purho of Nolla Games and the topics of scaling falling-sand worlds and destructible rigid-body integration. This verifies the broad case-study subject; exact algorithms in the registry remain local proposals until independently demonstrated. [Noita session](https://www.gdcvault.com/play/1025695/Exploring-the-Tech-and-Design)

## Scope limits that should survive later integration

This is a curated method library, not a copied tutorial or a declaration of universal taste. The large legacy archive was sampled rather than exhaustively audited. All originals and their embedded resources remain untouched. No asset licenses, embedded font rights, external executable snippets, live PixelLab capabilities, generated artwork quality, or runtime performance were certified by this work.

Each method now links to an executable reference fixture. The focused command is `python -W error::DeprecationWarning -m unittest tests.test_poc -v`; final per-test results are in the root verification report. Coverage includes failure injection, all-method coverage, report hashes, runner/source drift, missing-source refusal, temporary working directories and plugin resource resolution. The reference runner writes `poc-report.json` and eight PNGs to its selected output directory. `key-contact-sheet.png` contains positive then deliberately damaged rows; its columns show a flat mask, dark, light and checker backgrounds, with native-size and 4x views in each cell. The geometric check validates hole, shaft and tooth landmarks, while final visual acceptance remains separate.

A small array proof establishes its stated mathematical property only: it cannot establish live service behavior, full physics-engine stability, target-device performance, or final artistic quality. Preserve failed outcomes and unresolved visual reviews instead of turning them into passing capability claims.
